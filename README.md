# Trade Journal — SBI証券 収支分析

SBI証券からダウンロードしたCSVを読み込み、株式トレードの収支を集計・分析する
個人用のPWAです。**取引データは端末の中だけで処理され、外部に送信されません。**

## できること

- 累積損益カーブ、最大ドローダウン
- 勝率 / 期待値 / プロフィットファクター / ペイオフレシオ / 連勝・連敗
- 日次カレンダー（損益ヒートマップ）
- 週次・月次・四半期・年次の損益
- 銘柄別の成績（得意な銘柄・苦手な銘柄）
- 保有期間別（デイトレ / 持ち越し / スイング）
- 方向別（買い / 空売り）、商品区分別、曜日別、口座別
- 日付をタップすると、その日の全建玉の明細（建単価・決済単価・値幅・利確/損切り）
- **勝ち方の構造**：RR（平均利益÷平均損失）と、そこから決まる損益分岐に必要な勝率、
  実際の勝率との差（エッジ）。方向×保有・銘柄・テーマ・月・曜日の切り口別
- 損益の集中度、建玉金額と振れ幅、取引スタイルの時系列変化
- テーマ／セクター別の構成比
- **トレードプラン（事前記録）**：エントリー前に損切り価格・目標価格・持ち越す予定かを
  記録し、決済後にCSVと自動照合。R倍数・損切りを守れた率・予定外の持ち越しが測れる

## 使い方

### 1. SBI証券からCSVをダウンロードする

| CSV | 役割 |
| --- | --- |
| **約定履歴照会** | 主データ。全取引（新規・返済の両方）が入っている |
| **実現損益（譲渡益税明細）** | 現物・投資信託・米国株の損益を補完する |

約定履歴だけでも動きますが、**現物の損益は実現損益CSVが無いと出せません**。
約定履歴の現物売の行には売却代金しか入っておらず、平均取得価額の列が無いためです。

### 2. 「データ」画面でCSVを選ぶ

**両方を必ず取り込んでください。** 約定履歴だけだと現物・投資信託の損益が0として
集計され、米国株は1件も入りません（実データでは126件が損益0、合計が10,837円ずれる）。
取り込み漏れがあると画面上部に警告が出ます。

複数まとめて選べます。文字コード（Shift_JIS）の変換は自動です。
同じファイルを二度読み込んでも重複しません。

### 3. iPhoneで使う

配信URLをSafariで開き、共有メニューから「ホーム画面に追加」します。
以降はアイコンから起動し、**オフラインでも動作します**。

CSVはiCloud Drive等に置いておけば、iPhoneの「ファイル」から直接選べます。

## 設計上の判断

**損益は自前計算せず、SBIが算出した実額をそのまま使う。**
現物の平均取得単価、信用の金利・貸株料を自前で再現すると必ずSBIとズレます。
単価から再計算するのは、1回の決済が複数の建玉にまたがるときの数量按分のみです。

実データ（約定3,081件・13ヶ月）で検算した結果、
実現損益 −315,647円 / 手数料・諸経費 54,750円 がSBIの集計値と1円単位で一致しています。

**建玉はFIFO（先入先出）で突き合わせる。**
CSVには「どの新規建てをどの返済で決済したか」の対応が無いため、
銘柄・方向・区分・口座ごとに先入先出で組み立てます。SBIの建玉管理も原則FIFOです。
CSVに時刻列が無いので、同日内の順序は元CSVの行番号（`seq`）で復元します。

**記録に無い情報は、後から取り出せない。**

CSVには結果しか入っていない。そのため
「計画的に持ち越したのか、切れずに持ち越したのか」は原理的に判定できない。
実データでは「買いの持ち越し106件」が年間損失の72%を占めていたが、
それが手法の問題か執行の問題かは、この区別なしには決まらない。

`src/lib/plans.ts` の事前記録はこの限界への対処である。
損切り価格を必須にしているのは、そこが決まらないとリスク額が確定せず、

    R倍数 = 実現損益 ÷ (|エントリー価格 − 損切り価格| × 数量)

が計算できないため。−1Rより悪い決済は「決めた損切りを超えた」ことを意味し、
円建ての損益と違って建玉サイズが変わっても比較できる。

**勝率ではなくエッジを見る。**

損益がトントンになる勝率は RR だけで決まる（`必要勝率 = 1 / (1 + RR)`）。
したがって勝率の高低だけでは良し悪しが決まらず、見るべきは

    エッジ = 実際の勝率 − 損益分岐に必要な勝率

になる。勝率が高いのに負けている切り口は、必ず RR が低い。
`src/lib/edge.ts` がこの計算を担い、切り口ごとに並べる。

**分析は「傾向を見つける」より「見つけたつもりになるのを防ぐ」ことを優先する。**

8つの仮説（曜日×方向、セクター、ディスポジション効果、オーバートレード、市場別、
エントリー曜日、ポジションサイズ、ティルト）を実データで検証し、
それぞれに独立した反証を当てたところ、**7つが棄却された**。棄却理由は毎回同じ4つだった。

| 落とし穴 | 実測での現れ方 |
|---|---|
| 外れ値1〜2件が結論を作る | 曜日・保有区分の差は、上位2件を除くと p が 0.0013 → 0.3970 に消える |
| 同一日の建玉を独立標本として数える | 曜日と勝敗の関係は p=0.0022 → 日ブロックで p=0.1048 |
| 「純損益の N%」と「総損失の N%」の取り違え | ワースト10件は純損益比121% だが総損失比は17.0% |
| 非有意を「効果なし」と読み替える | 検出力不足と効果ゼロは別物 |

そのため分析画面はこう作ってある。

- 検定を含まない**確かな記述**（集中度・スタイル変化）を先に置く
- 検定はすべて**決済日をクラスタとして扱う**（`permutationByDayBlock` / `clusterBootstrapDiff`）
- 多重比較は **Holm補正**、検定本数と偶然当たる確率を画面に表示する
- 「差を検出」と書くには4条件すべてが必要：
  各群30件以上／補正後 p<0.01／各群から**上下1件ずつ**除いても符号が保たれる／前半と後半で符号が一致
- **差が出なかった軸も等しく列挙する**（多重比較の分母を隠さない）
- 乱数はシード固定。同じデータなら毎回同じ p 値が出る

現在のデータでは8軸すべてが「検出できず」になる。これは失敗ではなく結果である。

**色は損益の極性（diverging）で統一。**
青＝利益 / 赤＝損失、中点はグレー。日本の会計慣行（赤字）に合わせています。
カテゴリ配色は使いません — 同じ青が「利益」と「買い建て」の両方を意味する衝突を避けるためです。

## 構成

```
app/src/lib/sbi/     CSVの解析と建玉の突合
  types.ts           データモデル
  csv.ts             CP932デコード + CSVパース
  parse.ts           2形式の自動判別・解析・損益マージ
  positions.ts       FIFO建玉突合・保有期間区分
app/src/lib/
  analytics.ts       各種の切り口での集計
  edge.ts            RR・損益分岐勝率・エッジ。切り口別の比較
  stats.ts           検定と区間推定（日クラスタ補正つき）
  insights.ts        所見の自動生成。断定文を出す4条件を定義
  insights.worker.ts 検定をメインスレッドから追い出すワーカー
  sector-map.json    52銘柄の業種・テーマ分類
  plans.ts           トレードプランの事前記録・自動照合・R倍数
  db.ts              IndexedDB + バックアップ
  format.ts          表示整形
app/src/components/  グラフ・カレンダー・共通UI
app/src/views/       画面
```
